Character relationships

A proposal for tracking who matters to whom. Relationships are added on a character's card and drawn as a chart beside the roster. Everything here is clickable: pick a character, pick a line, try Edit. The cast is The Drowned Map sample, plus Ione (Wren's mother) and one archived character, Captain Dace, so the chart has something to show.

Click a character to put them in the middle. Click a line to read it.
The chart is the Characters drawer's second view. A Roster / Chart switch sits in the drawer header, and Chart opens the drawer full width (the existing Expand size), because a chart does not fit in 460px. One line per pair, colored by kind and always labeled, so color is never the only cue.
  • No saved layout. Everyone sits on a ring. Clicking a character moves them to the middle with their ties around them, so there are no positions to store or sync.
  • Kind filters in the side panel hide whole kinds of tie. Archived characters are off by default (screen 4).
  • The side panel shows the selected pair or character. Each pair has a line for how each one sees the other, because feelings are rarely mutual.
Characters
Relationships are added and edited on the card, in a new field under "Appears in", the same way cast and chapters already work. Each row names the other character, the kind, the label, and both points of view; clicking it opens the editor. "See on chart" switches to the chart with this character in the middle.
  • A pair is one record, so the tie shows on both cards (Wren's and Sela's) and editing either edits the same thing.
  • The card's subtitle gains a tie count beside the chapter count. Optional
One small dialog for adding and editing, in the style of Estoria's confirm dialog. Adding from Wren's card starts with Wren filled in, and the picker greys out anyone she already has a tie with, since a pair has one record.
  • Kind is a short fixed list that sets the color: Family, Friend, Romance, Mentor, Rival, Other. Label is free text for the specifics ("former mentor", "sisters").
  • Both points of view are optional. Leave one blank for a tie only one of them feels, or write "doesn't know she exists".
  • Changes over the story is shown greyed as a question, not a decision. It would let a tie turn at a chapter ("rival from Ch 3"). See the open questions.

Lines appear here as you connect your characters.

Open a character on the roster and use Add relationship. Each one you add shows up here as a line between two people.

Archiving keeps relationships, following Estoria's archive rule: Captain Dace leaves the roster and the picker, but his tie to Bram is kept and drawn dimmed and dashed when "Show archived" is on. Restoring him brings it back unchanged. Deleting a character removes their relationships too, and the delete confirm says how many ("They will be removed from 6 chapters and 1 relationship"). The empty state is plain and points at the one place relationships are added.
In the project file

One new list, next to characters

// StoryDoc gains one optional top-level field
relationships?: Relationship[]

interface Relationship {
  id: string;        // its own id, so merge treats it as a unit
  a: string;         // character id
  b: string;         // character id (a != b, one record per pair)
  kind: "family" | "friend" | "romance"
      | "mentor" | "rival" | "other";
  label?: string;    // "former mentor"
  aView?: string;    // how a sees b
  bView?: string;    // how b sees a
  notes?: string;
}

// Example
{ "id": "rel-k3x9", "a": "sela", "b": "wren",
  "kind": "mentor", "label": "former mentor",
  "aView": "Still sees her apprentice.",
  "bView": "Owes her everything, trusts her with nothing." }
What it touches

Sync, merge and the phone

  • No schema bump. The field is optional, like manuscript, author and pace before it. A file without it is a project with no relationships.
  • Series-wide. It sits beside characters, not on a book or version board, so every book in a series shares it and the phone needs no update first.
  • The phone keeps it. Android's normalize starts from the raw file and only overwrites keys it knows, so the list round-trips untouched. It just isn't shown there.
  • Read defensively. A tie whose character is gone (deleted on the phone, say) is dropped on read, as is a tie to itself or a second record for the same pair. An unknown kind reads as Other.
  • Conflicts and merge. Each relationship becomes its own row in the compare and merge dialog. Taking one from the file brings in both characters it points at.
  • Delete cleans up. Deleting a character removes its relationships; archiving keeps them.
