Android app at `main` `0f27338`. Findings only. Nothing in the app was changed.

**Method:** I read the diffs, the shared session notes, and the Android sync, diff and merge code.

**Severity rule**

- **Critical:** loses or corrupts data silently, with no saved copy to recover it from.
- **Should fix:** a wrong result or a silent loss that a saved copy, conflict copy or manual redo
  can still recover; or a real risk that grows with project size.
- **Nice to have:** polish, parity, hardening, or a cost that only shows at scale.

## Top findings

No critical findings. Every lossy path I found leaves a saved copy, a conflict copy, or something
the user can redo by hand. The five that matter most:

1. **S1. Bringing in a piece can silently drop that piece's edited characters, world entries and
   library items.** Records are merged by id and the anthology's copy wins. Copying a piece out,
   revising a character in the new project, then bringing it back loses the revision. The dialog
   says the opposite.
2. **S2. Bringing in a piece drops the piece project's Story notes.** A single piece shows Story
   notes in its Notes drawer, the dialog says "notes ... come in", and `bringIn` never copies
   `storyNotes`.
3. **S4. The phone can't see order changes, so a phone merge silently reverts the web's card
   order.** If the web reorders characters or world entries and the phone edits anything before
   syncing, the merge keeps the phone's order and writes it to Drive. No row is offered.
4. **S3. Map export of an anthology groups pieces by their old acts (web and phone).** A piece
   added to an anthology made from a three-act book is exported under Act I, out of reading order,
   and re-import scrambles the order.
5. **S7. Saved copies pile up with every image inside, and nothing warns before storage runs
   out.** Each form change, bring-in or move-out stores a full clone of the project in IndexedDB
   and writes another full file to the Drive folder.

## Should fix

### S1. Bring-in drops the incoming project's versions of shared-id records

- **Where:** `src/lib/anthology.ts:319-321` (`dedupeById(anth.X.concat(source.X))`). The dialog
  copy is at `src/components/modals/AnthologyModals.tsx:165`. The same pattern predates today in
  `mergeProjectIntoSeries` (`src/store/useStore.ts:1153`).
- **Failure scenario:**
  1. In an anthology, choose a piece › Make its own project › **Copy it out**. `takeOut` copies
     the characters it uses with **the same ids** (`anthology.ts:353`).
  2. In the new project, rewrite Kit's bio.
  3. Bring that project back into the anthology. `dedupeById` keeps the anthology's Kit, so the
     new bio is gone. The bring-in saved copy still has it, but nothing says so.
  4. Probe output: `bio after bring-in: old bio | characters: 1`.
  - **Variant (wrong record, not just a stale one):** two id-less assets in imported files both
    get `a-file-0` from `normalizeDoc` (`src/store/persistence.ts:1482`). After bring-in, the
    piece's pin resolves to the anthology's note, and the piece's own note is dropped.
  - The sample story's fixed ids (`wren`, `w1`… in `src/data/sampleStory.ts`) are a third
    source of collisions.
- **Dialog mismatch:** the dialog says "One typed separately in both shows up twice until you
  archive one". That holds only for different ids. For records with the same id, one copy is
  silently dropped.
- **Suggested fix:**
  - When an incoming record has the same id as an existing one but different content, give it a
    fresh `uid()`. Then rewrite the piece's `chars`, `worldRefs` and `refs[].assetId`, and the
    copied world entries' `refs[].assetId`, to the new ids. That keeps both versions, which
    matches the dialog.
  - Optionally offer "use the piece's version" when `source.savedCopy` or the take-out lineage
    shows it came from this anthology.
  - Apply the same treatment to `mergeProjectIntoSeries`.
  - Regression test: the probe in the Appendix.

### S2. Bring-in drops the piece project's Story notes

- **Where:** `src/lib/anthology.ts:299-324` never reads `source.storyNotes`. A piece's Notes
  drawer shows `doc.storyNotes` (`src/components/panels/NotesPanel.tsx:13`, `:61`). The dialog
  bullet at `AnthologyModals.tsx:159-161` says "Writing, map, notes, status, target: come in as one
  piece".
- **Failure scenario:** a poem project has research notes in its Story notes. Bring it into an
  anthology and the notes are gone from the anthology. They survive only in the "Before moving
  into an anthology" saved copy.
- **Suggested fix:**
  - Append `source.storyNotes` to the piece's own `notes`, under a small "From the project's
    notes" line, so the text stays with the piece and `takeOut` carries it back out.
  - Alternatively, add it to the anthology's Story notes under the piece's title.
  - Either way, make the dialog line say where the notes go.

### S3. Anthology map export groups pieces by their leftover acts (web and phone)

- **Where:**
  - Web: `src/lib/markdown.ts:109-113`. Acts are collected in array order, then chapters are
    filtered by act.
  - Phone: `app/.../lib/Markdown.kt:84-87`, with the same loop.
  - Pieces keep their old `act` (`toAnthology` leaves it). New and brought-in pieces get `act: 1`
    (`anthology.ts:241`, `:308`).
- **Failure scenario:**
  1. Turn a three-act book (chapters 1-3 in Acts I-III) into an anthology.
  2. Add a piece "Coda". It is number 4 and the last piece on the board.
  3. Export the map. Coda is listed under `## Act I` as `### 4.`, before Act II's `### 2.`.
  4. Importing that file builds a book in the order 1, 4, 2, 3.
  - In-app data is fine. Only the export, and anything rebuilt from it, is wrong.
- **Suggested fix:**
  - In both exporters, an anthology writes one `## Act I` heading and lists pieces with
    `inOrder` (by `num`). The importer still reads it, and the order is reading order.
  - Leave `act` itself alone, because Make this a book uses it.
  - Keep the web and phone outputs byte-identical, like the summary-line fix in `04c4fbd`.

### S4. Phone conflicts ignore character and world order, so a phone merge reverts the web's reorder

- **Where (Android):**
  - `lib/DocDiff.kt:47-66`, `docDiffSummary`, compares characters and world via `associateBy`,
    which loses order.
  - `lib/DocDiff.kt:128-145`, `DocUnit`, has no `charOrder`, `worldOrder` or `libraryOrder`.
  - `lib/Merge.kt:162-215` starts from the phone's lists and has no order step. The web's
    equivalents are `sync.ts:1322-1329` (`orderItem`) and `merge.ts:184-190` (`followOrder`).
- **What the phone actually says** (the "No differences" report, made precise):
  - **Order-only, characters or world:** the summary list is empty. The auto prompt reads "The
    Estoria file has newer changes (0 differences)." (`StoryViewModel.kt:397-400`). The sync
    sheet hides the headline when the list is empty (`SyncSheet.kt:150`). On Diverged, the merge
    dialog says "These copies differ only in details the merge can't name. Go back and keep one
    copy; the other is saved as a conflict copy." (`MergeDialog.kt:161-166`).
  - **Order-only, library:** `local.assets != remote.assets` compares lists, so the summary shows
    "Assets differ". The merge dialog still has no row for it, and shows the same "can't name"
    text.
  - "No differences" itself is `diffHeadline` on an empty list (`DocDiff.kt:94`).
- **Failure scenario (the silent one):**
  1. On the web, drag Kit to the top of the roster. Sync.
  2. The phone, offline, retitles a chapter. Now both sides have changed: Diverged.
  3. The phone's merge dialog lists only the chapter. "All phone" or a per-row merge keeps the
     phone's roster order, and the phone writes it.
  4. The web pulls it and Kit is back where he was. No row was offered, and no copy of the web's
     order was kept.
  - Low-stakes data (order can be redone), but silent.
  - RemoteAhead alone is safe: the phone pulls the whole file.
- **Suggested fix:**
  - Port `sharedOrder`, the three order units and `followOrder` to `DocDiff.kt` and `Merge.kt`,
    with the same keys (`doc:charOrder` and so on) so the address keys still match the web's.
  - Add "Character order differs" (and the world and library equivalents) to `docDiffSummary`.
  - Bump the phone's story-wide count to match. Rearranging stays web-only as Ray decided; only
    the merge learns order.

### S5. Partial merges in an anthology leave duplicate numbers and split sections

- **Where:** `src/lib/merge.ts:256-262`. A chapter taken from the file is `upsert`ed whole,
  including `num` and `section`. In an anthology, `num` is the only order and `section` is a run of
  consecutive pieces (`anthology.ts:56`, `:71-80`). The phone merge does the same.
- **Failure scenarios** (probe output in the Appendix):
  - Here, piece C is dragged to the front. In the file, B is retitled. Taking only B from the file
    gives `c:1 a:2 b:2`: two pieces numbered 2. The order then depends on array position.
  - Here, C is moved into "One". In the file, "One" is renamed "Harbor". Taking only A from the
    file gives the bands `One[c] Harbor[a] One[b] Two[d]`, so section "One" appears twice.
  - Follow-on effects:
    - `renameSection` renames both runs.
    - `moveSection` and `removeSection` act on the first run only (`anthology.ts:163-181`).
    - The selection bar builds React keys from the undeduped list, so they collide
      (`AnthologyView.tsx:223`, also N4).
- **Pre-existing for books** (duplicate `num` after a partial merge), but worse here, because
  order and sections are carried by these two fields alone.
- **Suggested fix:**
  - In an anthology, leave `num` and `section` out of the per-piece compare.
  - Diff them as one story-wide unit, "Piece order and sections", taken whole like the order
    units.
  - After any merge, `renumber(inOrder(...))`.
  - Mirror this on the phone.

### S6. Move out and bring in change only the version being viewed

- **Where:**
  - `src/store/useStore.ts:1301`: move out filters only `s.doc.chapters`.
  - `src/lib/anthology.ts:299-318`: bring-in inserts only into `anth.chapters`.
  - Every other version in `draftData` is untouched.
- **Failure scenarios:**
  - **Move out while viewing the main version:** the piece is still in every other version. The
    dialog said "It leaves the anthology". Switching versions brings it back, now alongside the
    new project.
  - **Bring in while viewing "Draft 2":**
    1. The piece exists only in Draft 2, and the source project has left the project list.
    2. Later, delete Draft 2 or make another version main. The piece is gone from the anthology.
    3. Recoverable only from the bring-in saved copy.
- **Suggested fix:**
  - Simplest: apply both to every version (`mapVersions`, as `toAnthology` already does). Bring-in
    inserts the piece into each version; move out removes it from each.
  - Alternatively, allow these only while viewing the main version and say so in the dialogs.

### S7. Saved copies grow storage with no limit and no warning before the quota

- **Where:**
  - `src/lib/piece.ts:170-177`: `makeSavedCopy` is a full `structuredClone`, images included.
  - It is stored in `projectStash`. IndexedDB keys images by project id (`src/store/images.ts`),
    so the base64 is duplicated per copy.
  - `src/lib/sync.ts:590-599` writes another full file to the Drive folder.
  - Nothing prunes saved copies. Nothing calls `navigator.storage.estimate()`. The only warning is
    the Footer message after a save has already failed (`src/components/Footer.tsx:494-499`).
- **What today adds:** four new triggers: Make anthology, Make book, Bring in, and Move out (one
  copy per move).
- **Size per copy:** pictures are downscaled to a 2048 px edge at JPEG 0.85 (`src/lib/files.ts`).
  A typical photo is about 0.3-0.8 MB, or about 0.4-1.1 MB as base64. An anthology with 20 pinned
  photos is therefore about 10-20 MB per saved copy, in the browser and again in Drive.
- **Failure scenario:**
  1. Ray moves eight pieces out of a picture-heavy anthology, one at a time.
  2. That makes eight full copies: about 80-160 MB of IndexedDB and eight more large files in the
     Drive folder.
  3. On Safari or iPad, where storage is tighter and evictable, this can reach the quota. The next
     ordinary save then fails, and that failure is the first warning.
- **Suggested fix, in order of payoff:**
  1. Before a change of form, check `storage.estimate()` and warn above about 80% use.
  2. In the Projects list, a "Saved copies: N, X MB" line with Delete for each copy, or a
     keep-the-newest-N rule that asks before deleting.
  3. Store each image once, keyed by content hash, so saved copies share pictures instead of
     duplicating them.

### S8. The phone reads the whole project file into one String

- **Where (Android):** `ui/StoryViewModel.kt:321` and `ui/AppRoot.kt:234`, `:290` call
  `readText()` on the whole file. `stashBackup` then encodes the document again
  (`StoryViewModel.kt:451`). The manifest does not set `android:largeHeap`.
- **Failure scenario:**
  - `src/lib/driveFolder.ts:79` already plans for 15-18 MB projects.
  - An 18 MB file is a 36 MB UTF-16 String. Add the parsed JSON tree, the decoded doc, and an
    encode for the backup, and peak memory on a mid-range phone is several times the file size.
  - Anthologies make big files likelier, because each bring-in adds a whole piece's images into
    one file. The likely outcome is an OOM crash on open or sync.
  - Not verified on a device. Pre-existing, made more likely by today's work.
- **Suggested fix:**
  - Measure peak memory with a 20 MB fixture on an emulator.
  - Decode from the stream (`Json.decodeFromStream`).
  - Skip the extra encode when a backup is identical.
  - Warn when the file is over about 15 MB.

## Nice to have

### N1. Drawer tiles re-render the whole list on every document change

- **Where:**
  - `src/components/panels/CharactersPanel.tsx:13` subscribes to the whole `doc`.
  - `:53` computes `chapterCount` per tile, which is characters × chapters.
  - `:127` looks up `roster.find` inside the `order.map`, which is O(n²).
  - `src/components/panels/WorldPanel.tsx:66`, `:77`, `:140` have the same pattern.
  - `DetailCard` is not memoised.
- **Scenario:** a roster of 300 characters in a 150-chapter book, with the Characters drawer
  open. Every keystroke in the character window, or anywhere in the document, re-renders 300
  tiles, about 45k `includes` checks plus about 90k `find` steps. That's a few milliseconds of
  script plus reconciling 300 cards, and noticeable on an iPad. At today's typical cast sizes
  (under 50) it is not noticeable. Not measured.
- **Suggested fix:**
  - Count appearances in one pass into a `Map` (`useMemo` on `chapters`).
  - Look tiles up in a `Map` by id.
  - Select narrow store slices.
  - Wrap `DetailCard` in `React.memo` with stable callbacks.

### N2. Tile drag details

- **Where:** `src/components/ui/useTileReorder.tsx`.
- **Ref churn:** `itemRef(id)` and `gripProps(id).ref` (`:344-355`) are new functions on every
  render. React therefore detaches and reattaches every tile's ref on each render: two `Map`
  operations per tile. Cheap, but avoidable with a cached callback per id.
- **Click swallow on touch:** the swallow listener is removed after `setTimeout(…, 0)`
  (`:266-267`). On touch browsers the synthetic click can arrive in a later task. Dropping a card
  back on itself could then open its window. Verify on the iPad and on Android Chrome; if it
  happens, keep the swallow for a short window (about 400 ms) or check a "just dragged" flag in
  `DetailCard`'s click handler.
- **Layout reads:** `measure()` reads every tile's rectangle on each order change during a drag
  (`:110-118`). That's fine into the hundreds.

### N3. The anthology board's drag is mouse-only

- **Where:** `src/components/AnthologyView.tsx:142-160` uses HTML5 `draggable` and `dataTransfer`.
- **Scenario:** on the iPad (Safari) and on phone browsers, pieces can't be dragged between
  sections. The piece menu's Move to section still works.
- **Suggested fix:** reuse the pointer-event approach from `useTileReorder`.

### N4. Duplicate section names break keys and section actions

- **Where:** `src/components/AnthologyView.tsx:223` uses `key={name}` over
  `all.map(b => b.section)` without deduping. `src/lib/anthology.ts:155-181` covers rename, move
  and remove.
- **Scenario:** after S5, or after two "No section" bands, React sees duplicate keys and the
  rename, move and remove actions behave as described in S5.
- **Suggested fix:** dedupe the list. Then on load, either merge same-named runs, or rename the
  later run "Name (2)" and tell the user.

### N5. Inactive versions and books skip the piece-field checks

- **Where:** `src/store/persistence.ts:1594` passes `draftData` through as-is. `pieceFields` runs
  only on the top-level `chapters`.
- **Scenario:** a hand-edited or foreign file has `kind: "novel"` in a non-active version.
  `kindInfo` falls back, so nothing crashes. The kind picker shows nothing selected until the
  writer picks one.
- **Suggested fix:** run `pieceFields` over every version's and book's chapters.

### N6. Picture sources aren't restricted to `data:`

- **Where:**
  - `src/store/persistence.ts:1459-1490` (`normalizeAssets`) keeps any `src`, and `coverSrc` is
    the same.
  - They are rendered at `src/components/ui/RefList.tsx:405`, `:597`,
    `src/components/SeriesMap.tsx:528` and `src/components/Lightbox.tsx:21`.
  - `index.html` has no CSP.
- **Scenario:** an imported or brought-in project carries `src: "https://tracker.example/p.png"`.
  Opening the Notes drawer makes the browser fetch it, which leaks the writer's IP address and the
  time of the visit. The new tile grid shows pictures as soon as a drawer opens.
  - Not script execution. I found no HTML sinks; see Security.
- **Suggested fix:**
  - Accept only `data:image/*` and `blob:` in `normalizeAssets` and for `coverSrc`.
  - Add `<meta http-equiv="Content-Security-Policy" content="img-src 'self' data: blob:">`. Extend
    it to the other directives once their needs are checked (Drive, the sign-in broker, fonts).

### N7. Moving a piece out leaves chapter links pointing at it

- **Where:** `src/store/useStore.ts:1301` removes the chapter without touching `links`.
  `deleteChapter` (`:1520-1529`) bridges the gap instead.
- **Scenario:** in an anthology the links are hidden. After Make this a book, the board's chain is
  broken where the piece was. The Board skips the missing end (`src/components/Board.tsx:438`), so
  nothing crashes. The file carries dead links.
- **Suggested fix:** drop and bridge links the way `deleteChapter` does.

### N8. Phone map-export title differs from the web's

- **Where:** Android `lib/Markdown.kt:39-40` uses the active book's title in all cases. Web
  `src/lib/markdown.ts:67-68` uses it only in a series, and `projectTitle` otherwise.
- **Scenario:** a standalone book whose book record is titled "Book 1" exports as `# Book 1` on
  the phone and `# Salt and Lantern` on the web.
- **Suggested fix:** use the web's rule. This was noted in `anthology-android.md` and not yet done.

### N9. Web tiles say "chapters" in an anthology

- **Where:** `src/components/panels/CharactersPanel.tsx:102` ("in N chapters") and
  `src/components/panels/WorldPanel.tsx:110` ("on N chapters").
- **Gap:** the phone already says "pieces" here (`29a77d0`).
- **Suggested fix:** use piece wording when `isAnthology(doc)`.

### N10. Bundle growth

- **Measured** with `vite build`, main JS chunk:
  - Before (`a52fb13`): 681.0 KB raw, 207.3 KB gzip.
  - After (`8084767`): 731.0 KB raw (+50 KB, +7.3%), 222.4 KB gzip (+15 KB).
  - CSS went from 44.3 KB to 47.3 KB.
  - It is one chunk, already over Vite's 500 KB warning.
- **Suggested fix:** lazy-load the anthology view and its modals, the export builders (docx, zip),
  and the less-used modals.

### 1. Android gaps, ranked by impact

Checked and fine:

- The phone round-trips the new chapter keys (`kind`, `keepLineBreaks`, `section`) through
  `Chapter.extra`.
- Its chapter diff includes those extras, so a section-only change shows a row (the Kotlin
  `ChapterSerializer` is an `ExtrasSerializer`).
- Book versus anthology is merge-blocked on both apps.
- The new saved-copy reasons (`anthology`, `book`, `bringin`, `takeout`) match the phone's
  `-saved-[a-z]+-` file pattern.
- The restyle (tiles, windows, chips) needs no phone change; the phone has its own UI.

### 2. Security

- **No new HTML sinks.** There is no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or
  user-controlled `href` anywhere in `src/`. Tiles, windows, chips, piece pages and section names
  all render as React text.
- **Exports:**
  - The docx path escapes `& < > "` (`src/lib/manuscriptExport.ts:114`) and builds piece and
    section titles through `runsFor`.
  - Markdown and plain-text exports are text files, so a `#` in a title is cosmetic.
- **Imported and brought-in projects:**
  - They go through `normalizeDoc`.
  - Bring-in only takes projects already in the project list (`canBringIn`).
  - The remaining exposures:
    - Remote picture URLs (N6).
    - Id collisions (S1), which are a data-integrity issue, not a security one.
- **Drive scope:** unchanged, `drive.file` plus `openid email` (`src/lib/driveConfig.ts:28`). That
  is the narrowest scope that works.
- **Logs:** no new logging. The only `console.*` call in the app is the render-error boundary
  (`src/components/ErrorBoundary.tsx:61`).

### 3. Performance

- **Tiles and windows with large casts:** see N1. Fine at today's sizes; at 300 characters it is a
  whole-list re-render on every keystroke.
- **Drag handlers:**
  - The preview order changes only when the target slot changes.
  - The store commits once, on release.
  - Auto-scroll runs on one `requestAnimationFrame` loop.
  - Small inefficiencies are in N2.
- **Anthology board with many pieces:**
  - `bands()` is a sort plus one pass per render. That's fine at hundreds of pieces.
  - The board re-renders on every doc change (`AnthologyView.tsx:39`), the same pattern as N1.
- **Sync and merge:**
  - The order units add three O(n) passes.
  - `followOrder` is O(n log n).
  - Saved copies cost one `structuredClone` of the whole doc per change of form, which is
    noticeable only with many pictures (S7).
- **Bundle:** +50 KB raw, +15 KB gzip (N10).

### 4. Save-file stability

- **Round trips:**
  - The web keeps unknown chapter keys and validates the three piece fields (`pieceFields`).
  - The phone keeps them in `extra`.
  - No field is dropped in either direction.
  - The gap: inactive versions skip validation (N5).
- **`normalizeDoc`:**
  - `form: "anthology"` is dropped inside a series, by design.
  - A stray `kind`, `keepLineBreaks` or `section` value is dropped. Fine.
- **Merge conflicts on order and anthology fields:** S4 (phone order), S5 (piece order and
  sections).
- **Copy-first conversions:** every one takes a saved copy first, which is good. The gaps:
  - S1: bring-in drops the incoming project's versions of shared-id records.
  - S2: bring-in drops Story notes.
  - S6: move out and bring in touch only the version being viewed.
  - N7: links are left behind when a piece moves out.
- **Dangling references:**
  - Take-out copies exactly the characters, world entries and assets the piece uses, including
    assets pinned to those world entries.
  - The S1 variant is the one way a reference ends up pointing at the wrong record.
- **Schema and back-compat:**
  - No schema bump. `SCHEMA_VERSION` is still 9.
  - All new fields are optional.
  - An older web build would show an anthology as a plain book, and its form unit would differ in
    a merge.
  - Card order is plain array order, so nothing new to migrate.

### 5. Size limits

- **What grows:**
  - Base64 pictures: each brought-in piece brings its images in.
  - Saved copies: each one is a full project.
  - Prose and maps are small by comparison.
- **localStorage (~5 MB per origin):** holds only the project maps now. Prose and pictures are in
  IndexedDB (`src/store/prose.ts`, `src/store/images.ts`). Not a limit in practice.
- **IndexedDB:** the real browser limit.
  - Chrome allows a share of free disk.
  - Safari is tighter and can evict a site that isn't installed. `storageDurability.ts` asks for
    persistent storage.
  - Saved copies are what fill it (S7).
- **Drive:**
  - The file-size limit (terabytes) is irrelevant.
  - Uploads over 4 MB already go resumable on both apps (`src/lib/drive.ts:15`, Android
    `DriveApi.kt:91`), so the 5 MB simple-upload cap is handled.
  - The Drive folder does accumulate saved-copy files (S7).

## Relationship chart: how it adds to the risks

Based on `docs/PLAN-relationships.md` on `claude/relationship-chart-4c8990`. Nothing is built yet.

- **S1 gets worse.** Relationships and `relationshipLayout` are keyed by character id.
  - Bring-in has to union the source's relationships, kinds and layout. Today's `bringIn` doesn't
    know about them, as the anthology note already flagged.
  - Take-out has to copy the ties between the characters it copies.
  - The id collision in S1 would reattach a brought-in tie to the anthology's same-id character.
    Fix S1 first, or re-id endpoints together with the characters.
- **The phone merges all three new keys as one unit.**
  - `relationships`, `relationshipKinds` and `relationshipLayout` all fall into the phone's
    "Other story settings" unit (`DocDiff.kt:641-646`), taken as one set.
  - So a phone merge takes every relationship from one side.
  - Taking "Other" from the file while keeping the phone's characters can leave dangling
    endpoints. The web's loader then drops those ties silently.
- **Load churn after a phone delete.**
  1. The phone deletes a character and writes the file with that character's ties still in it.
  2. The web drops the dangling ties when it loads (plan step 2).
  3. The loaded doc no longer matches the file's fingerprint, so the web writes it back. If the
     phone edits in between, that can become a conflict.
  - Fix: prune on the web's next write, not at load, or have the phone drop the ties when it
    deletes the character.
- **Unit count:** the story-wide count goes from 12 to 14 (kinds and layout) plus the
  per-relationship collection. Remember `sync.test.ts`, and S4's phone port, which should include
  these as well.
- **Performance:**
  - Commit chart drags on release only. Writing `relationshipLayout` on every `pointermove` would
    re-render every whole-`doc` subscriber (N1) and dirty autosave and sync on each frame.
  - Label collision avoidance is O(labels × obstacles). Cap the work or cache the result for large
    casts.
- **Hardening:** build `relationshipLayout` with `Object.create(null)` or a `Map` when normalising,
  so a hand-edited key such as `__proto__` can't touch the object prototype.
